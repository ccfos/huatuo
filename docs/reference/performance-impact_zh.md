## 1. 概述

### 1.1 评估目的

- 量化 HUATUO 的各项采集功能开启前后，业务吞吐、请求延迟及错误情况的变化。

- 量化常驻运行、事件触发和指标采集活动带来的进程及整机资源开销。

- 识别高负载、较大采集规模和异常场景中的性能影响及恢复情况。

- 为功能启用、配置选择和版本评估提供可复现的依据。

### 1.2 测试范围与不包含的范围

评估计划按九类功能组织。业务负载涵盖 Redis、etcd、H2、BuntDB、fakeredis、Dragonfly、DaCapo 和 Flaskr，另用 fio、Neper 构造存储和网络压力。

本次不覆盖所有功能同时开启的整体部署、长期稳定性，以及未列出的平台和业务负载。

测试结论适用于对应的被测构建、配置和负载；微基准与业务负载的结果分别列示。

## 3. 评估方法与指标

### 3.1 对照状态

基线组和开启组使用相同业务参数与测量工具。网络测试在关闭模块后复测，profiling 在停止采样后复测，用于观察性能漂移。系统异常测试在故障解除后继续观察，期间保持原有模块开关状态。

存储基线为无本次 HUATUO 测试进程。网络与系统异常以目标模块关闭为基线，连续快照以采集器空闲为基线，CPU profiler 以采样前的业务测量为基线。全 metrics 以保留采集模块、无主动抓取为基线。

### 3.2 指标与计算方法

B 为基线值，E 为开启值。表头区分“吞吐变化率”和“吞吐下降率”。例如从 100 降到 95 ops/s，变化率为 −5%，下降率为 5%。基线为零或缺失时，相对变化率记为 N/A。

| 指标 | 计算或统计方式 | 单位 |
| --- | --- | --- |
| 吞吐变化率 | (E − B) / B × 100%，负值表示吞吐下降 | % |
| 吞吐下降率 | (B − E) / B × 100% | % |
| 延迟 / 耗时增长率 | (E − B) / B × 100% | % |
| 资源增量 | E − B | CPU 核、MiB 等 |
| CPU 使用率差 | 开启使用率 − 基线使用率 | 百分点；注明单核或整机 |
| P99 / P99.9 | 对应测量窗口请求延迟的分位数 | ms |
| 均值与峰值 | 分别报告，峰值注明采样间隔 | 随指标 |
| 错误与超时 | 记录数量及请求总数；缺失标待补充 | 次数 / % |

系统异常另用阶段变化差：100 × \[(ON故障 / ON健康 − 1) − (OFF故障 / OFF健康 − 1)\]，单位为百分点，负值表示开启侧退化更多。该值与直接吞吐下降率分开列示。

### 3.3 测量窗口与结果汇总

| 测试类别 | 预热 / 测量 | 重复及汇总方式 |
| --- | --- | --- |
| 内存 | 预热 120s、稳定 15s、资源窗口 180s；native 业务取约 120s 写入窗口 | 计划每场景 3 对 B/C。Go/BuntDB 连续快照汇总第 1、3 对，其余场景见 4.1.5。按组均值计算变化。 |

## 4. 模块性能影响评估

### 4.1 内存（BPF 与用户态快照）

#### 4.1.1 测试对象与范围

| 模块 | 测试范围 |
| --- | --- |
| memsnapshot | Go/BuntDB、Python/fakeredis、Java/H2 的连续串行快照，以及 Java、Python 内存扩展对照。 |
| Native profiler | Go/BuntDB、C/Redis、C++/Dragonfly 的 virtualalloc、physicalalloc、physicalusage。 |
| Java profiler | Java/H2 的 objectalloc、object_usage，统计插入和删除操作。 |

BPF 挂载点、挂载条件及读写文件清单待按被测版本核对。

#### 4.1.2 测试方案

在同一物理机上对同一负载做 B/C 配对。连续快照的 B 组保持采集进程空闲，C 组在 180 秒内连续串行采集。Profiler 的 B 组关闭采集，C 组开启对应模式。每个场景执行三对，记录业务请求、采集输出及业务和采集器的 CPU、内存。

#### 4.1.3 场景与参数矩阵

| 场景 | 业务负载 | 关键参数 |
| --- | --- | --- |
| 常规连续快照 | Go/BuntDB、Python/fakeredis、Java/H2 | 4 GiB 容器。Go、Python 预载 49,152 个 64 KiB 键并持续 GET。Java 固定 3 GiB 堆，预载 524,288 行并持续 JDBC 点查。 |
| Java 连续快照扩展 | Java/H2 | 容器限额 4 / 10 / 19 GiB，固定堆 3 / 7.5 / 15.5 GiB，分别预载 524,288 / 1,048,576 / 2,097,152 行。 |
| Python 连续快照扩展 | Python/fakeredis | 8 / 16 GiB 档分别预载 13 万 / 26 万个 64 KiB 键，容器限额 10 / 19 GiB。 |
| Native profiler | Go/BuntDB、C/Redis、C++/Dragonfly | 持续读取热键，以每秒 250 条的计划写入 30,000 个 64 KiB 冷键，随后集中删除。两种物理模式均为 100% 采样。 |
| Java profiler | Java/H2 | 每三次查询插入并删除一条临时记录。统计第 20～150 秒内完整执行的插入与删除对。 |

#### 4.1.4 评价指标与统计口径

| 场景 | 业务指标口径 |
| --- | --- |
| 连续快照 | 按 180 秒统计 GET 或 JDBC 点查吞吐及 P99/P999，并记录采集次数和采集时间占比。 |
| Native profiler | 按实际冷键写入窗口统计热键 GET 吞吐及 P99/P999。集中删除单独核对。 |
| Java profiler | 处理速率为完成的插入与删除对数除以累计操作耗时。P99/P999 按每对耗时计算，排除查询和空闲时间。 |

业务及采集器 CPU 和内存按全程统计。变化率按 C 组均值除以 B 组均值再减 1 计算，尾延迟均值取各轮分位数的算术平均。

#### 4.1.5 测试结果

| 场景 | 负载 | 吞吐或处理速率变化 | P99 变化 |
| --- | --- | --- | --- |
| 连续快照 | Go/BuntDB，第 1、3 组 | +0.78% | −0.29% |
| 连续快照 | Python/fakeredis | −0.99% | −0.54% |
| 连续快照 | Java/H2 | −2.07% | +0.32% |
| 连续快照扩展 | Java/H2，16 GiB 档 | −2.46% | +1.36% |
| 连续快照扩展 | Python/fakeredis，8 GiB 档 | +2.57% | −0.97% |
| 连续快照扩展 | Python/fakeredis，16 GiB 档 | +1.65% | −0.63% |
| Native profiler，物理模式最大影响 | Go/BuntDB | −8.52% | +24.39% |
| Native profiler，物理模式最大影响 | C/Redis | −1.67% | +32.94% |
| Native profiler，物理模式最大影响 | C++/Dragonfly | −2.85% | +18.95% |
| Java profiler objectalloc | Java/H2 | −1.11% | +2.78% |
| Java profiler objectusage | Java/H2 | −1.99% | +5.34% |

Go/BuntDB 连续快照排除了波动较大的第 2 组。Native profiler 的最大影响按两种物理模式逐指标取值。

#### 4.1.6 结论与限制

**连续内存快照。** Go/BuntDB 排除波动组后，吞吐 +0.78%、P99 −0.29%。Python/fakeredis 吞吐 −0.99%、P99 −0.54%。Java/H2 吞吐 −2.07%、P99 +0.32%。

**内存扩展。** Java/H2 在 4、8、16 GiB 三档的单次快照耗时中位数为 117～122 ms，16 GiB 档吞吐 −2.46%、P99 +1.36%。Python/fakeredis 实测 RSS 从 7.99 GiB 增至 15.94 GiB 后，180 秒内采集次数减少约 41%，两档均未观察到吞吐下降或 P99 上升。

**Native profiler。** 100% 物理采样下，按实际冷键写入窗口统计热键读取。Go/BuntDB、C/Redis、C++/Dragonfly 的吞吐分别最多下降 8.52%、1.67%、2.85%，P99 分别最多增加 24.39%、32.94%、18.95%。Redis 实测定位到新页分配时同步取栈增加了请求延迟。

**Java profiler。** 仅按插入和删除的累计耗时计算处理速率。objectalloc 处理速率 −1.11%、P99 +2.78%，objectusage 处理速率 −1.99%、P99 +5.34%。

结果适用于本次单机、业务负载和采集配置。Native profiler 的集中删除阶段单独核对，未计入上述吞吐和 P99。

### 4.2 内存回收

#### 4.2.1 测试对象与范围

`memory_reclaim` 统计直接回收次数，通过 /metrics 的 `huatuo_bamai_memory_reclaim_directstall` 核对计数。`memory_reclaim_events` 在 `try_to_free_pages` 的入口和返回处记录直接回收耗时，达到阈值后上报事件。测试工具读取 /proc/vmstat，分别统计直接回收和 kswapd 后台回收的页数。`memory_free_compact` 暂时缺少可精确测量的结果。

#### 4.2.2 测试方案

分别在基线和仅开启目标模块时施加相同压力。第一组降低 cgroup 内存限额，观察回收固定数量的文件缓存需要多久。第二组先填充文件缓存，再由多个工作线程同时申请内存，观察全机直接回收和后台回收。

#### 4.2.3 场景与参数矩阵

| 模块 | 负载与参数 | 配置与核对项 |
| --- | --- | --- |
| memory_reclaim | 预载 256 GiB 干净文件缓存，将限额降至 128 GiB | 发压进程绑定 CPU 2，采集器绑定 CPU 18–23，记录回收耗时和模块计数 |
| 全机直接回收事件 | 1024 GiB 文件缓存，突发申请 1023 GiB，保留 1 GiB，180 个工作线程绑核 | 跨 NUMA 节点交错分配，事件耗时阈值设为 0，检查 OOM 和换出页数 |

#### 4.2.4 评价指标与统计口径

### 4.5 系统异常

#### 4.5.2 测试方案

### 4.6 网络（BPF）

本节统一记录 dropwatch、tcp_retransmit、net_rx_latency、irqtracing、softirq 五项 Feature 的业务影响及极限性能影响。五项均使用 BPF 钩子，不再按 metrics/events 拆分到4.7。数据来自已完成实验，整理日期为2026-11-17。

下文保留历史单轮原值，失败及未齐三次的组合不计作三次完成。

#### 4.6.1 测试对象与范围

**模块与钩子**

除标明 kprobe、raw tracepoint 的条目外，均为 tracepoint。

| Feature | BPF钩子 | 描述及覆盖范围 |
| --- | --- | --- |
| dropwatch | `skb/kfree_skb` | 在丢包路径执行过滤、采集内核栈并输出事件 |
| dropwatch，可选 | `raw_tracepoint/devlink_trap_report` | 内核支持且启用硬件自动检测时观察devlink trap；本批未证明硬件丢包覆盖 |
| tcp_retransmit | `tcp/tcp_retransmit_skb`、`tcp/tcp_retransmit_synack` | 观察数据、SYN及SYN-ACK重传 |

irqtracing平时读取CPU统计，触发后才挂载采栈钩子。softirq是持续分桶统计，测量等待延迟，不是软中断执行时长；无逐事件perf输出或独立事件文件。

共用两机调度、Feature控制、负载、采集、统计和清理流程，五项逐项开启，不复制各Feature的测试主流程。

### 4.7 网络异常事件

#### 4.7.1 测试对象与范围

`netdev_events` 记录接口链路状态变化。测试使用临时 veth 接口对，本端保持 up，切换对端状态。

`netdev_hw` 在每次 /metrics 请求中对所有匹配的 netdevsim 接口逐一触发 BPF 快照。两组均衡量 bamai 进程开销。具体 BPF 挂载点和文件访问路径未在本次记录中列出。

#### 4.7.2 测试方案

- **netdev_events：**创建 veth pair，本端保持 up，对 peer 执行 down→up。每个 peer 每秒 1/10/50 个完整循环，接口数量为 1/10/50 对。

- **netdev_hw：**创建 1/10/50 个 netdevsim 接口，每秒并行发起 1/10/50 个 `/metrics` 请求并持续循环，每个请求采集所有匹配接口。

- **观测 bamai：**CPU user/sys/total（core）、RSS、FD、goroutine，并与同配置关闭目标 case 的对照组计算差值。

- 除目标 case 外全部加入 BlackList，不限制 bamai 资源。

- **base 对照组：**接口数量、目标发压方式、预热和采样时长与目标组相同，bamai 仍运行，但目标 case 也加入 BlackList；仍有 HTTP、Go/runtime 和进程指标等基础开销，不是“不运行 bamai”或“无负载”的组。

#### 4.7.3 场景与参数矩阵

| 测试对象 | 接口规模 | 每秒目标负载 | 一次操作 |
| --- | --- | --- | --- |
| 链路状态事件（veth） | 1 / 10 / 50 对 | 每个对端执行 1 / 10 / 50 个循环 | 同一对端按 down、up 顺序切换，各对端并行。每个循环预期产生两条 carrier 事件 |

| --- | --- | --- |
| 直接随机读 | 4K | 1／1、256／1、256／32 |
| 直接随机读 | 64K、256K | 分别为 256／1、256／32 |
| 直接随机写 | 4K | 256／1、256／32 |
| 直接随机写 | 64K、256K | 分别为 256／1、256／32 |

| 直接顺序写 | 1M | 16／4 |

| 缓冲随机读、缓冲顺序写 | 256K | 各测 1／32 |
| 逐次 fsync 写 | 4K | 1／1、1／32 |
| mmap 顺序读、mmap 顺序写 | 4K | 无 QD 参数，各测 1、32 个 worker |

fio 每个 job 使用独立的 64 MiB 文件，准备和预读不计入测量窗口。

```bash
taskset -c "$CPUS" fio --name=filesystem-io-perf --directory="$DATA" --filename_format='job.$jobnum' --size=64m --numjobs="$JOBS" --cpus_allowed="$CPUS" --cpus_allowed_policy=split --ioengine="$ENGINE" --direct="$DIRECT" --invalidate="$INVALIDATE" --rw="$RW" --bs="$BS" --iodepth="$QD" --time_based --runtime=15 --ramp_time=2 --randrepeat=1 --randseed="$ROUND" --allow_file_create=0 --group_reporting --eta=never --output-format=json --output="$OUT/fio.json" "${EXTRA_ARGS[@]}"
```

直接 I/O 使用 `libaio`，`DIRECT=INVALIDATE=1`。缓冲 I/O 和逐次 fsync 写使用 `psync`，`DIRECT=INVALIDATE=0`。`RW` 按场景取 `read/randread/write/randwrite`。Bash 数组 `EXTRA_ARGS` 在读场景为 `(--readonly)`，逐次 fsync 写为 `(--fsync=1)`，其余为空。`DATA` 位于私有测试文件系统，`OUT` 位于 tmpfs。

mmap 每次访问 4 KiB，遍历文件后回收映射。读场景同时回收自身文件缓存，写场景执行 flush。吞吐包含这些操作和负载程序自身开销。

iotracing 的抓取时长覆盖负载窗口，`DEVICE_ID` 指向测试文件系统所在设备。

```bash
"$IOTRACING" --bpf-path "$BPF_OBJECT" --device "$DEVICE_ID" --duration "$CAPTURE_LIMIT" --output json --max-process 4096 --max-files-per-process 4096
```

#### 4.9.4 评价指标与统计口径

| 指标 | 含义与统计方式 |
| --- | --- |
| 吞吐量，MiB/s | fio 的实测读写速率，mmap 按访问字节数除以实际测量时长。各状态取有效轮次的算术平均值 |
| IOPS | fio 每秒完成的操作数，用于衡量小块 I/O 的负载强度 |
| Redis OPS | 服务端命令计数增量除以实际测量时长，多实例取合计 |
| P50、P95、P99、P99.9，ms | 客户端请求往返时间分位数。先合并各客户端和各轮的逐请求直方图，再求分位数 |
| 性能变化 | `(开启值 − 关闭值) / 关闭值 × 100%`。吞吐为负表示下降，延时为正表示变慢 |
| 轮间波动 | 各侧最小值和最大值相对该侧均值的偏差，按 `(观测值 − 均值) / 均值 × 100%` 计算 |

结果按“关闭 → 开启（变化）”展示。变化率由未舍入的统计值计算。

#### 4.9.6 结论与限制

- 块层采集的主要降幅出现在 4K、QD256、单进程随机读。IOLatency 单开下降 8.33%～11.44%，三项全开下降 8.07%～11.74%。blk-throttle 和 IOCOST 在无实际限速等待时，单开下降均小于 1%。

- Redis 的主要降幅出现在 AOF always。8 实例、128 总连接时，仅开 iotracing 吞吐下降 5.82%～5.93%，四项全开下降 6.39%～6.67%。单实例四项全开的 P99 上升 5.70%～13.71%。

## 6. 结论与使用建议

### 6.1 总体结论

现有结果可用于选择上线前优先验证的功能和负载。对延迟敏感的服务，优先复测实际使用的采样频率、抓取周期和存储模式，并同时核对吞吐与尾延迟。



### 6.2 使用建议

| 使用场景 | 配置与验证建议 | 依据 |
| --- | --- | --- |
| Python CPU 采样 | 分别在拟用频率和停采状态测吞吐、P99。100 Hz 在本次 Flaskr 负载下仍有可见吞吐损失。 | 4.4.5 |
| 物理内存采样 | 按目标应用验证采样期间的请求长尾。计划降低采样率时，另测该档位。 | 4.1.5 的物理模式为 100% 采样。 |
| 小块 I/O 或同步持久化 | 按实际块大小、队列深度和 AOF 策略单测 iotracing，再验证完整部署组合。 | 4.9.5、5.2 |
| 多容器 metrics 抓取 | 记录一轮抓取的实际耗时，再设置周期。在实际容器数和并发下同时观察 Bamai CPU 和业务 P99.9。 | 4.8.5 |
| hungtask | 用生产日志级别和预期阻塞任务数验证抓栈期间的业务延迟。 | 4.5.5 |
| 网络 BPF | 使用目标发布构建发压，核对目标事件的计数、采栈或发布记录，再解释业务变化。 | 4.6.6 |
