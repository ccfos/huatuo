## 概述

持续性能剖析将采集期间的 CPU 时间、等待时间和内存分配归因到调用栈，帮助分析资源消耗来自哪些代码路径。结合资源指标，可从异常节点或容器进一步定位到需要检查的函数。

剖析按指定时长执行，并按采集模式生成周期窗口或单次结果。可通过 API 管理节点和容器任务，也可在目标节点直接运行 `profiler`。

## 适用场景

| 问题 | 剖析方式 | 可获得的线索 |
| --- | --- | --- |
| CPU 使用率升高，需要查找热点 | on-CPU | 各调用栈消耗的 CPU 时间 |
| 请求变慢，但 CPU 使用率不高 | off-CPU | 阻塞与等待调度的调用路径 |
| 内存分配频繁，需要定位分配来源 | 原生内存或 Java 对象分配 | 分配量及分配调用栈 |
| 内存占用持续增长，需要检查存活分配 | 物理页存活量或 Java 存活对象 | 采集覆盖范围内的存活量及分配路径 |

热点和存活量是排查线索，不能单独证明性能瓶颈或内存泄漏。应结合业务负载、采集范围和时间窗口分析。

## 采集能力

### CPU

| 模式 | 支持语言 | 统计内容 |
| --- | --- | --- |
| on-CPU | C、C++、Go、Java、Python | 按采样频率记录调用栈，折算 CPU 时间 |
| off-CPU | C、C++、Go | 记录线程离开 CPU 后的阻塞和调度等待时间 |

原生采集使用 eBPF，Java 使用 async-profiler，Python 使用 py-spy。off-CPU 为事件驱动采集，可区分阻塞与运行队列等待；它不等同于业务请求的端到端延迟。

### 内存

| 模式 | 支持语言 | 统计内容 |
| --- | --- | --- |
| `virtual_alloc` | C、C++、Go | 虚拟地址空间分配量 |
| `physical_alloc` | C、C++、Go | 采集窗口内的物理内存分配量 |
| `physical_usage` | C、C++、Go | 本次采集跟踪的物理页存活字节数 |
| `object_alloc` | Java | 对象分配量及分配调用栈 |
| `object_usage` | Java、Python | JVM 存活对象，或 Python 进程存活分配的字节数及分配调用栈 |

Python 内存采集使用预编译 Memray 运行时，支持 Linux glibc、x86-64 和 AArch64 上的 CPython 3.7–3.14。结果是附加之后分配、采集结束时仍未释放的字节数，不包含更早的分配，也不等同于 RSS。运行 profiler 的环境必须在 `PATH` 中提供 `gdb`，并允许通过 `ptrace` 附加目标；seccomp 和 Yama `ptrace_scope` 不能阻止附加。命令行可选择 Python、原生或混合调用栈。

同一个 Python 进程同时只能有一个 Memray 会话；重复请求会失败，不会中断已有采集。向容器复制运行时时会拒绝绝对符号链接和越过目标根目录的链接，请使用目录或不越界的相对链接。

Python 内存结果只有在收到运行时的流结束标记（trailer）后才会发布。取消采集后最多等待两秒读完剩余记录；强制关闭连接或未收到结束标记就遇到 EOF 时，采集失败，不会发布不完整的存活内存结果。目标进程等待初始数据连接的时间上限为十秒，收到取消请求也会退出等待。

`physical_usage` 不包含采集前分配的页，也不按采样概率倒数放大，不能作为进程完整 RSS。其页释放识别等边界仍待验证和完善，具体限制见[性能剖析实践](/docs/best-practice/continuous-profiling_zh.md#物理内存存活量)。

## 采集方式

| 方式 | 适用范围 | 依赖 |
| --- | --- | --- |
| Profiling API | 远程创建、查询和停止节点或容器任务 | huatuo-apiserver、huatuo-bamai；结果查询需要 Elasticsearch |
| `profiler` 命令行 | 在节点上采集目标进程，也支持原生 CPU 宿主机或容器采集 | Linux 采集环境及相应工具；本地输出无需 API 服务或 Elasticsearch |

支持的语言、模式和目标范围以当前版本能力为准；原生采集还需满足内核能力和采样权限要求。

## 结果

### 火焰图

火焰图展示调用路径及其累计值：宽度表示 CPU 时间、等待时间或所选内存维度的字节数；纵向表示调用深度，横向位置不表示时间先后。可以沿较宽的栈帧检查资源消耗来源。

![宿主机 CPU 火焰图与函数统计](/docs/img/continuous-profiling-grafana-host.png)

结果可在 Grafana 中查看，也可输出为本地 SVG、折叠栈或 JSON，供离线分析和后续处理。

### 采集窗口

原生 CPU、内存和 Java 采集按周期处理数据，Python 在采集结束后输出一次。窗口时间表示接收和聚合区间，不是精确的逐样本执行时间。

物理页存活量使用最新快照，不能跨窗口累加。比较不同结果时，应保持采集目标、模式、时间范围及业务负载具有可比性。

### 完整性

任务状态、结果发布和丢样统计共同决定结果的可用性。失败任务可能保留部分已写数据，看到火焰图不代表任务已成功完成；空结果也不代表没有资源消耗。

部署步骤、任务 API、命令行示例和结果验证方法见[性能剖析实践](/docs/best-practice/continuous-profiling_zh.md)。
